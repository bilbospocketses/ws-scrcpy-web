Understanding TLS Certificates: The "Subject Name" Explained Simply

If you have ever seen the small padlock icon next to a website address in your browser, you have seen a TLS certificate at work.

A TLS certificate acts like a digital ID card or passport for a computer server on the internet or private network. It ensures two main things:

  1. Privacy: The conversation between your computer and the server is encrypted (scrambled so eavesdroppers cannot read it).
  2. Identity Verification: You are actually talking to the exact computer you intended to reach, not an imposter.

1. What is the "Subject Name"?

Think of a TLS certificate as a government-issued passport:

  • A passport lists your Legal Name to prove who you are.
  • A TLS certificate lists a Subject Name (or Subject Alternative Name / SAN) to prove which server address it belongs to.

When your computer connects to a server, the server shows its certificate. Your computer inspects the Subject Name on that certificate and asks:

"Does the name or address I typed in the web browser's address bar match the name officially stamped on this ID card?"

  • If it matches: The connection proceeds securely (green lock / secure badge). When the browser connecting to the website trusts the certificate. See the Installing a Certificate (Establishing Trust) section below.
  • If it doesn't match: Your browser flashes a warning saying, "Your connection is not private" or "Certificate name mismatch."

2. Addresses vs. Names: The Real-World Analogy

To understand how connections work, imagine sending mail:

3. How the Connection Works (Step-by-Step)

Scenario A: Connecting Using a Domain Name (FQDN)

This is what happens when you visit https://bank.example.com.

  1. You type the name: You enter bank.example.com into your address bar.
  2. Name Resolution (DNS): Your computer does not know where bank.example.com physically lives on the network, so it asks a DNS server (the internet's address book):

    "What is the IP address for bank.example.com?"

    DNS replies: "It's at 203.0.113.10."

  3. Reaching the Server: Your computer contacts the computer sitting at 203.0.113.10.
  4. Showing the ID: The server hands over its TLS certificate.
  5. The Verification Check: Your computer looks at the certificate's Subject Name.
    • It sees: Subject: bank.example.com.
    • Your computer says: "I asked for bank.example.com, and this certificate says bank.example.com. Perfect!"
    • The secure connection is established.

Scenario B: Connecting Using a Short Hostname (Internal Network)

Inside an office or home network, people often use short nicknames instead of full domain names (e.g., connecting to a printer or internal server named backup-server).

  1. You type the nickname: You go to https://backup-server.
  2. Local Name Resolution: Your office router or local directory looks up the name backup-server and finds its local address (e.g., 10.0.0.15).
  3. The Certificate Check:
    • If the certificate's Subject Name specifically lists backup-server, the connection succeeds.
    • Common Issue: If the certificate only lists the full name (backup-server.local or backup-server.company.com), your computer throws an error because the short nickname you typed does not match what is printed on the certificate.

Scenario C: Connecting Directly to an IP Address

Sometimes, technical administrators connect directly to an IP address (for example, typing https://192.168.1.1 to open a home router's settings).

  1. No Lookup Needed: Because you provided the exact numerical coordinates, your computer skips the address book (DNS) entirely and goes straight to 192.168.1.1.
  2. The Certificate Check: The server hands over its certificate, and your computer looks for an IP Address entry in the certificate's Subject Alternative Names.
  3. The Outcome:
    • If the certificate has IP: 192.168.1.1 embedded inside it: The check passes.
    • If the certificate only has domain names (e.g., router.lan): Your computer warns you of a mismatch, because you typed numbers (192.168.1.1), but the ID card only claims the text name (router.lan).

4. Installing a Certificate (Establishing Trust)

Matching the name in the address bar is only half of the identity check. Your operating system and browser must also trust who issued the ID card.

  • Public Certificates: When you visit sites like Google or your bank, their certificates are signed by well-known, globally recognized Certificate Authorities (CAs). Operating systems and browsers come pre-loaded with these trusted issuers.
  • Private / Internal Certificates: For local home labs, intranet servers, or private appliances, you create your own Certificate Authority. Because your devices do not recognize this new authority out of the box, you must install the root certificate once on every computer connecting to it.

The certificate ws-scrcpy-web downloads (Settings → Local HTTPS → download ca certificate) is named ws-scrcpy-web-local-ca.crt.

Follow the instructions below for your specific operating system or browser:

Jump to: Windows · macOS · Linux · Android · iOS / iPadOS · Firefox

Windows

  1. Double-click the downloaded certificate file (.crt).
  2. Click Install Certificate....
  3. Under Store Location, select:
    • Local Machine (Recommended): Makes the certificate trusted for all accounts on the PC (requires an administrator confirmation).
    • Current User: Makes the certificate trusted only for your current sign-in account.
  4. Click Next, choose Place all certificates in the following store, and click Browse....
  5. Select Trusted Root Certification Authorities and click OK.
  6. Click Next, then Finish. If a security confirmation warning appears, click Yes.
  7. Restart your web browser.

macOS

  1. Open Keychain Access (press Cmd + Space, type Keychain Access, and press Enter).
  2. In the left sidebar, choose the System keychain.
  3. Drag and drop your downloaded certificate file directly into the list.
  4. Double-click the newly added certificate to open its settings window.
  5. Expand the Trust section.
  6. Set When using this certificate to Always Trust.
  7. Close the window and authenticate with your administrator password or Touch ID when prompted.
  8. Restart Safari or your browser.

Linux

Linux manages system certificates through background command-line utilities. Both GNOME and KDE desktop environments rely on these underlying system stores for Chromium-based browsers, cURL, and system tools.

Ubuntu / Debian Variants (Ubuntu Desktop, Pop!_OS, Linux Mint)

  1. The ws-scrcpy-web download already ends with .crt, which is what this folder needs. (A certificate obtained elsewhere that ends in .pem or .cer must be renamed to end in .crt first.)
  2. Copy the file into the system CA folder: 
    sudo cp ws-scrcpy-web-local-ca.crt /usr/local/share/ca-certificates/
  3. Update the system trust database: 
    sudo update-ca-certificates

Fedora / RHEL Variants (Fedora Workstation, CentOS Stream, Rocky Linux)

  1. Copy the certificate file into the source anchors folder: 
    sudo cp ws-scrcpy-web-local-ca.crt /etc/pki/ca-trust/source/anchors/
  2. Update the system trust database: 
    sudo update-ca-trust

(Note for GNOME & KDE desktop users: While tools like GNOME's "Passwords and Keys" or KDE's "Kleopatra" display keys, running the commands above ensures all system software and desktop browsers pick up trust immediately.)

Android

  1. Download the certificate file to the device (or transfer it over USB/local share).
  2. Open Settings → Security & privacy (or Security).
  3. Tap More security settings → Encryption & credentials (or Credentials).
  4. Tap Install a certificate → CA certificate.
  5. Read and tap Install anyway on the warning prompt, then verify your identity with your PIN, fingerprint, or pattern.
  6. Select your downloaded certificate file from the file picker.

iOS / iPadOS

Apple requires a mandatory two-step installation and trust procedure:

  1. Step 1: Install the profile
    • Download the certificate in Safari or AirDrop it to your device.
    • Tap Allow when prompted to download a configuration profile.
    • Open Settings, where a Profile Downloaded prompt will appear near the top (or go to Settings → General → VPN & Device Management).
    • Tap the downloaded profile, tap Install in the top-right corner, enter your device passcode, and confirm.
  2. Step 2: Turn on Full Trust
    • Go to Settings → General → About.
    • Scroll down to the very bottom and tap Certificate Trust Settings.
    • Under Enable full trust for root certificates, find your certificate and turn the toggle switch to ON.
    • Tap Continue to confirm the prompt.

Using Mozilla Firefox?

Unlike Chrome, Edge, and Safari (which read directly from Windows, macOS, or Linux system certificate stores), Mozilla Firefox uses its own isolated certificate database:

  1. Open Firefox and go to Settings (or type about:preferences#privacy in the address bar).
  2. Click Privacy & Security in the left sidebar.
  3. Scroll down to the Certificates section and click View Certificates....
  4. In the Certificate Manager popup, select the Authorities tab.
  5. Click Import... at the bottom.
  6. Choose your downloaded certificate file.
  7. In the prompt that opens, check the box for Trust this CA to identify websites.
  8. Click OK, close preferences, and refresh your target website.

5. Key Takeaways

  1. The Rule of Matching: Whatever you type in the address bar must appear on the certificate's Subject Alternative Name (SAN) list.
  2. DNS finds the location; the Certificate proves identity: DNS translates a friendly name into an IP address so your computer can reach the machine. The certificate proves that the machine at that address is legitimately authorized to represent that name.
  3. Trust + Matching = Secure: Both requirements must be satisfied: the address must match what's printed on the ID, and the root authority that issued it must be installed in your device's trusted store.
  4. IP addresses are harder to certify: Public certificate authorities rarely issue certificates for raw public IP addresses and never issue them for private LAN IPs (such as 192.168.x.x). Private IP setups require self-issued certificates imported via the steps in Section 4.
